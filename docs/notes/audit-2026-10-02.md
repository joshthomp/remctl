# RemCTL audit — October 2, 2026

Reviewed `0788f4b..00c20ee` and the local changes on top of 2.1.0. The existing No Priority smart-list fix and default blue color were preserved. Changes remain local; this is not a public release.

## Changes

- Smart-list filtering and pinned counts reuse lightweight reminder fields within each request. Tags and location alarms are queried only when a filter needs them. Full details, attachments, and saved links are loaded only for the returned page. Removed the unused `detail` argument and an unreachable duplicate filter branch.
- Statistics aggregate total, active, overdue, flagged, and urgent counts in one reminder scan instead of five. Deleted or missing lists, empty stores, and nullable completion flags retain their previous behavior.
- Workspace Today, Overdue, Scheduled, and due-date sorting use the date Reminders displays. Claude Code uses that same date for labels and overdue counts. Both previously used the raw due date in places even though the CLI already used the displayed date.
- Claude Code hides Undo after completing a repeating reminder. Marking the reminder incomplete cannot restore the occurrence that just advanced. Ordinary reminders keep Undo.
- The installer path that reuses an existing protected Python runtime now packages both plugins and the Codex marketplace before signing. Previously that path installed a healthy host but left Codex unable to refresh the plugin.
- A zoned reminder with an absolute alert exactly one local UTC offset away from its due time no longer triggers the floating-time heuristic. Only ambiguous dates need an indexed alarm lookup; UTC dates need none. Reminders with no time zone keep the GoodTask behavior from #49, and deleted alarms do not override the legacy fallback.

## Due-time reproduction

The CLI and MCP tools read reminder dates from the signed host. Agents rely on `dueDate` when editing reminders, while `displayDate` describes the time Reminders shows.

1. Create a disposable reminder due October 3 at 16:00 in Rome, with an absolute alert at 15:00.
2. Move its due time to 17:00, keeping the custom alert.
3. Before the fix, `get_reminder` reports 15:00 as the due time and omits `displayDate`. The stored due time is still correct: the reader mistook the two-hour difference for a floating date.
4. A later edit can consequently treat the custom alert as a due-time alert and move it.

This requires an exact offset match, not every custom alert. The regression test covers Rome and New York, genuine floating dates, deleted alarms, and the UTC fast path. The live edit matrix verifies both the first and a second reschedule while retaining the custom alert.
